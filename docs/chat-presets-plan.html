Chat presets implementation plan

Add a fast, show-scoped preset workflow to the chat composer. A preset is a named template such as Put {{mic}} in {{mix}} at {{level}}. Each unique placeholder has one field definition and can be filled as a microphone, mix, text, number, or predefined option before sending.

User flow

  1. A presets button appears on the inline-start side of the existing message input group.
  2. The dialog opens on a searchable/scannable preset list. Selecting one immediately shows only its required fields.
  3. Microphone and mix fields use the current show's live lists; text and number use focused inputs; option fields use predefined choices.
  4. The dialog shows a live message preview. “Send” resolves the fields, sends the rich message, and closes the dialog on success.
  5. “New preset” opens a compact builder: name, template, and one automatically generated configuration row per {{placeholder}}.
  6. Existing presets can be edited or deleted from the same dialog, with destructive actions kept explicit.

Data and contracts

Area Plan
Preset definitions Add a chat_presets table in chats.db, keyed by a typed preset id and scoped to a show. Store the template and validated field definitions as JSON. Use the existing startup table creation pattern; do not add a migration or change versions.
Messages Keep the existing chat_messages.body column. Normal messages remain plain strings. Rich preset messages are stored in a versioned JSON envelope containing fallback text and typed render parts.
Compatibility Decode the envelope defensively. Invalid, unknown, or legacy rows render as ordinary text, preserving replay and reconnect reliability.
RPC Extend chat state with presets; add create/update/delete preset mutations; allow send to accept optional validated message parts.

Shared logic

  • Put placeholder extraction, preset validation, template resolution, envelope encoding, and envelope decoding in the contracts package.
  • Require unique placeholder names and a matching field definition for every placeholder.
  • Resolve to both accessible fallback text and typed parts. Mic/mix parts carry a stable id plus the sent label, name, and color so old messages do not visually change when show data changes.
  • Enforce the existing 4,000-character visible-message limit on the resolved fallback text.

Message rendering

Render text, number, and predefined-option values inline as normal text. Render microphone and mix values as compact semantic badges with their saved color and number/label, plus a visible mic or speaker icon. Preserve whitespace and wrap long messages safely.

Verification

  • Contract tests for placeholder parsing, resolving repeated placeholders, validation, and safe envelope fallback.
  • Backend service tests for preset CRUD, show isolation, rich-message round trips, and deletion with the show.
  • Frontend tests for pure builder/selection helpers where practical, followed by repository checks, tests, and builds.
  • Manual browser pass for creating a preset, filling every field type, sending, reconnect/reload persistence, editing, deleting, empty states, and keyboard behavior.
