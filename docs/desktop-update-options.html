Showtime · Desktop distribution research

Updates that wait for the engineer

A comparison of Electron update strategies, grounded in Showtime's current packaging and its highest-risk constraint: update downloads and installation must never consume show resources, stop the local backend, disconnect clients, or restart the app unless the engineer explicitly asks.

Recommended direction

✓

Use electron-updater with a launch check and manual updates

Keep electron-builder and the current NSIS, DMG, and AppImage targets. Publish signed artifacts and builder-generated update metadata to public GitHub Releases initially. Check availability once in the background on launch, then put download and installation behind user actions and a backend-owned live-session guard.

  • Check once after launch without delaying startup. Do not poll or schedule further checks during the session.
  • Discovery only updates a passive status indicator. Separate Download and Install & restart buttons keep costly or disruptive work explicit.
  • Refuse and cancel downloads while any Live session is active; re-check the guard atomically before installation and immediately before quitting.
  • Start with GitHub Releases because the repository is already public; move the same metadata and artifacts to static object storage later without replacing the update client.
The library defaults still do not meet Showtime's policy. In the currently configured electron-builder generation, automatic download and install-on-quit are enabled by default. Set autoDownload = false and autoInstallOnAppQuit = false. If the project upgrades to electron-updater 7 / electron-builder 27, use autoInstallEvent = "manual". Do not use the convenience method checkForUpdatesAndNotify(); call checkForUpdates() once and handle its result in Showtime's own passive UI.

Why this fits this repository

The update mechanism is not an isolated desktop feature. Showtime's main process owns the backend that browsers and mobile devices use during a show, so installation is a coordinated service shutdown.

01

electron-updater with GitHub Releases or static HTTPS

Recommended

electron-builder generates platform metadata such as latest.yml, latest-mac.yml, and latest-linux.yml. The app checks that metadata, downloads a signed artifact, verifies it, and installs only when the application calls the install method. It supports progress, cancellation, differential downloads, and staged rollouts.

Why it wins
  • Matches all configured targets.
  • Least packaging churn.
  • Enough events for an automatic check and honest manual update UI.
  • Provider can change without changing the user flow.
Watch carefully
  • Defaults perform work automatically.
  • Production behavior must be tested from installed packages.
  • macOS signing is mandatory; Windows signing is strongly advised.
  • Rollback still requires publishing a higher version.
02

Electron autoUpdater and update-electron-app

Electron's built-in updater uses Squirrel.Mac and, for traditional Windows apps, Squirrel.Windows. The convenience package update-electron-app checks on startup and every ten minutes by default, downloads in the background, and prompts to restart. It can use the free Electron update service for public GitHub apps, but the service supports only Windows and macOS.

Showtime could customize the built-in API to check only after a click, but a discovered update is still downloaded automatically. More importantly, the project would replace its working Windows NSIS target and still need an unrelated Linux solution. That is packaging churn without a reliability benefit.

03

Microsoft, Apple, and Linux distribution channels

Stores and system package managers provide trusted delivery, review, signing, and centralized upgrades. They are useful additional installation channels once Showtime is mature. They are not a single cross-platform self-update system, and background update policy can be controlled outside the app—directly conflicting with a strict “download and install only when requested inside Showtime” promise.

Treat them as later distribution channels. A store build may need to omit the in-app updater and explain that updates are managed by the store.

04

A custom updater

A custom manifest and download flow offers exact policy control, but the hard part is safe replacement: signature verification, atomicity, elevation, locked files, interrupted installs, architecture selection, proxy behavior, partial releases, and platform-specific rollback. This duplicates mature updater logic in one of the highest-risk parts of the app. It is only justified if a future deployment model cannot be represented by existing providers.

Product behavior contract

Discovery may be automatic; change remains manual

The policy belongs in the main/backend boundary, not only in a disabled React button. Renderer state can be stale, a second client may be Live, and the session can change between download and install.

Showtime never…

  • polls, schedules recurring checks, or checks because a window was reopened;
  • downloads merely because the launch check discovered an update;
  • installs on normal quit, OS shutdown, or the next launch;
  • starts or continues update downloads or installation while Live is active;
  • quits if any Live lease exists or the safety state is unknown;
  • turns an update failure into an app-startup or backend failure.

Showtime only…

  • checks once, asynchronously, after the packaged app and backend have started;
  • downloads after an explicit Download action;
  • installs after Install & restart plus confirmation;
  • performs each download/install step when the backend says no show is Live;
  • acquires an exclusive maintenance permit before shutting down;
  • shows recoverable errors and leaves the running version untouched.
Launch Start normally

The backend and window do not wait for the update service.

Automatic · once Check quietly

Fetch metadata only; show a passive result and never auto-download.

User action 1 Download

Refuse if Live; expose progress; cancel if Live begins.

User action 2 Install

Confirm restart and ask the backend for a maintenance permit.

Protected exit Drain & replace

Dispose backend cleanly, install, relaunch, and report the new version.

A route check is not enough. Today a Live session is renderer-local, and connected PWAs can be Live independently of the host window. Add a backend-owned registry of short-lived Live leases. Each Live UI registers and renews a lease; leaving unregisters it; expiration handles crashes and disconnects. Installation obtains an exclusive maintenance permit only when the lease set is empty and prevents a new lease from starting during shutdown. If the guard cannot answer, fail closed and do not install.

Suggested implementation shape

Keep platform mechanics behind one small service

Updater events are callback-based and global. Wrap them once in the main process, expose a narrow state machine over the preload bridge, and let the web UI remain declarative.

Backend: LiveGuard

An Effect service owns Live leases and an exclusive maintenance permit. RPC lets connected browser clients register/renew/release their Live presence.

Main: DesktopUpdateService

Owns electron-updater, translates events to a typed state, serializes commands, enforces timeouts, logs failures, and checks LiveGuard before every transition.

Renderer: Settings / About

Displays current version and one valid next action. It never talks to the update host directly and never decides whether quitting is safe.

State Primary UI Allowed command Failure behavior
idle Current version Check again after a failed launch check Remain on installed version
checking Checking… None Return to idle with retryable message
available Version, size, release notes Download Keep metadata; allow retry
downloading Progress and cancel Cancel Delete/ignore partial data; never install
ready Install & restart Install after confirmation Stay ready unless validation failed
blocked-live “Available after Live ends” None Return to previous safe state after Live
Handle updater quit separately. Electron's updater closes windows before the normal before-quit sequence in some paths. Showtime's current backend cleanup relies on before-quit, so the update path should explicitly drain and dispose the backend before invoking the installer, and also listen for before-quit-for-update as a defensive path.

Path to an installable product

The implemented release foundation

  1. Establish version and release rules

    The desktop package now starts at 0.1.0 with a tag-driven semver rule. Never reuse a published version. Correct a bad release with a newer version rather than replacing assets under the old tag.

  2. Make packages trustworthy

    Sign Windows builds. Sign and notarize macOS builds. Add zip beside dmg. Make release CI fail rather than silently publish unsigned production artifacts.

  3. Build a repeatable matrix release

    Build on each native OS, run tests, publish installers and update metadata to a draft GitHub Release, smoke-test fresh installs, then publish. Keep metadata publication last.

  4. Add the authoritative LiveGuard

    Model host and remote Live presence as leases in the backend. Test disconnect, crash, reconnect, stale lease expiry, and the install-versus-Live race before updater integration.

  5. Add the launch-check update service and manual update UI

    Use typed IPC contracts, explicit commands, cancellation, log files, and a fail-closed maintenance permit. Show release notes as plain text or sanitized content; never inject remote HTML.

  6. Test real upgrade paths

    Test n → n+1 on installed Windows, macOS Intel/Apple Silicon as supported, and AppImage. Cover no network, proxy, corrupt metadata, bad checksum/signature, partial download, disk full, Live starting mid-download, shutdown, and backend disposal failure.

  7. Roll out conservatively

    Use an internal channel first, then a small stable cohort or staged metadata. Monitor successful checks/downloads/installs without collecting show content. Preserve a manual installer link as the recovery path.
