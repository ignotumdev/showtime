Unified SQLite state, prerelease reset, and migrations

Replace Showtime's backend JSON files, per-show documents, and separate chat database with one authoritative .showtime/showtime.db. Build it on Effect SQL's Node SQLite client and migrator, establish the complete current schema as migration 1, reject every prerelease state format, and remove code made obsolete by the new architecture.

Decisions

This is a clean cutover, not a data conversion. Showtime must never import, decode, rewrite, or otherwise accept settings.json, profiles.json, connections.json, chats.db, show JSON files, old stored-chat envelopes, or any earlier experimental showtime.db schema.

  • A fresh showtime.db is initialized exclusively by 0001_initial. This is the version-1 first-release baseline.
  • If any known prerelease backend state exists, startup fails with an actionable developer-facing reset message, even when a current database also exists. It does not silently ignore, delete, or import that state.
  • An existing showtime.db is accepted only when Effect's migration ledger and current-schema validation agree. Unknown, missing, renamed, or future migration state fails closed.
  • After the first public release, only versions of showtime.db produced by a released Showtime build may migrate forward. Prerelease JSON and database formats never become migration sources.
  • Browser local storage remains device-local because remote browsers cannot access the host database. It stores credentials and device preferences only; it is not an authoritative copy of backend state. Its current payloads are strict version 1.

1. One Effect SQL database

Database layer

  1. Replace ChatDatabase with a backend-wide database module that resolves .showtime/showtime.db from HomeDirectory and returns SqliteClient.layer through Layer.unwrap.
  2. Use the @effect/sql-sqlite-node client directly. Its single connection is already serialized, scoped, cached, and WAL-enabled by default; do not add another connection pool or global write mutex.
  3. Configure PRAGMA foreign_keys = ON, PRAGMA busy_timeout = 5000, and the selected durability policy before the migrator runs. Prefer synchronous = FULL for Showtime's reliability-first requirements and verify its soundcheck/live performance.
  4. Compose configuration, migrations, baseline bootstrap, and current-schema validation as layers. Provide a DatabaseReady service only after all four succeed. Every repository and server layer depends on that readiness boundary.
  5. Keep database acquisition and shutdown scoped. Use the SQLite client's native backup Effect for consistent backups instead of copying a live database and WAL files manually.

Canonical schema

AreaTables and invariants
Application settings A singleton app_settings row contains connection enablement, host name, and the default profile foreign key. A database constraint enforces its singleton identity.
Profiles profiles stores typed IDs, unique normalized names, colors, and UTC timestamps. The default profile cannot be removed while referenced by settings.
Connections connection_clients, connection_invitations, and normalized scope tables preserve capabilities, expiry, profile ownership, and least privilege. Capabilities and tokens never appear in logs.
Shows shows, microphones, mixes, songs, song_mix_assignments, and song_microphone_names replace the show documents. Foreign keys and ordering columns preserve ownership and stable UI order. Soft-delete columns retain the current domain semantics.
Chat Keep the existing channel, message, profile-channel-state, and preset concepts in the same database. Store current message metadata in explicit columns or strict JSON columns validated with Effect Schema; do not retain v1/v2/v3 string prefixes.

Use foreign-key cascades only when deletion is unquestionably owned by the parent. Use explicit service operations when revocation, soft deletion, or user confirmation is part of the domain behavior. Add indexes for every foreign key and hot list/order query. Do not copy the JSON files' per-document version fields into relational rows; migration 0001_initial is the database-wide schema version.

2. Effect-native repositories and transactions

  1. Keep domain repositories as Context.Service classes with focused layerNoDeps layers requiring SqlClient and DatabaseReady. Compose live dependencies with Layer.provide or Layer.provideMerge; avoid hidden runtimes inside services.
  2. Define reusable request and result schemas at SQL boundaries. Use SqlSchema.findAll, findOne, findOneOption, and void so parameters are encoded and unknown rows are decoded through Effect Schema in the typed error channel.
  3. Implement effectful methods with named Effect.fn functions. Use Schema.TaggedErrorClass for database, persistence, and consistency errors, then translate them to RpcError only at the service/RPC boundary.
  4. Wrap every multi-statement mutation in SqlClient.withTransaction. Rely on Effect SQL's nested savepoints rather than home-grown nested locking. Return results only after commit.
  5. Remove persisted Ref mirrors from shows, profiles, settings, and connections. Query SQLite as the authority. Keep Ref only for truly ephemeral process state such as active WebSocket session handles.
  6. Adapt SyncEngine so a mutation runs its SQL transaction before publishing reactivity invalidations. Queries no longer need its global semaphore. A failed or rolled-back transaction must never emit a new snapshot.
  7. Preserve the current client-generated song ID and idempotent retry behavior, but make songs.create.id required and enforce uniqueness in SQLite.

3. Baseline migration and startup

  1. Add packages/backend/src/database/migrations/0001_initial.ts. It creates the entire current schema, constraints, and indexes in one migration Effect requiring SqlClient.
  2. Load it with Effect's SqliteMigrator.fromGlob when the desktop build is verified to include migration modules; otherwise use SqliteMigrator.fromRecord with static imports. Do not implement a custom migration loader or ledger.
  3. Run SqliteMigrator.layer after the client and PRAGMAs and before repositories. Effect owns effect_sql_migrations, duplicate detection, locking, transactions, spans, and pending-step selection.
  4. Follow migrations with an idempotent bootstrap transaction that creates the first profile and singleton settings row only in a fresh baseline database. Host-derived values and generated IDs do not belong in DDL migration modules.
  5. Validate the exact current migration ledger and critical schema invariants before providing DatabaseReady. Migration success is not permission to accept an unknown prerelease database that merely has similarly named tables.

There is no JSON-to-SQL import step. Legacy-file detection is a guard that fails startup; it is not migration 0. Tests must prove that placing any old file beside a missing current database never creates or populates showtime.db.

4. Remove obsolete and dead code

ShowFile, ShowPaths, ShowDiscovery Delete filesystem persistence/discovery and their tests. Remove path-bearing repository entries and show-file persistence errors/contracts that have no planned import/export consumer.

parseShowId, MAIN_DIST Remove the unused exports.

Retain JSON only as a future explicit import/export format if product requirements call for portable shows. Such files are not watched, discovered, or accepted as application state, and no prerelease show document is implicitly importable.

5. Security, durability, and operations

  • Create the data directory and database with owner-only permissions where supported. Verify permissions for the database plus -wal and -shm files.
  • Keep capability comparison and revocation server-side. Parameterize every query; never interpolate capabilities, tokens, IDs, or user input into SQL text.
  • Add startup PRAGMA quick_check or a deliberately scheduled integrity check whose latency is measured on realistic show databases. Surface failure before serving RPC.
  • Provide a scoped backup service around SqliteClient.backup. Define retention and restore separately before release; do not mix backup policy into migrations.
  • Annotate migrations and repository operations with non-sensitive structured metadata and spans. Never log row payloads from chat or connection tables.

Implementation sequence

  1. Add rejection tests for every prerelease file/database shape and strict version-1 browser records before changing persistence.
  2. Build the shared SQLite client, PRAGMA, migrator, bootstrap, validation, and test layers. Prove fresh startup, repeated startup, failure, and packaged migration loading.
  3. Add migration 1 with all tables, constraints, and indexes. Exercise foreign keys and transaction rollback in isolated temporary databases.
  4. Port settings, profiles, and connections first so host-name changes and credential revocation become one transaction.
  5. Port show, microphone, mix, and song repositories; preserve stable ordering, soft deletion, optimistic mutation results, and idempotent song creation.
  6. Move chat onto the shared client and current relational representation. Remove its inline schema setup and encoded-body compatibility.
  7. Rewire backend layers so migrations/bootstrap gate repositories and network startup, then delete obsolete persistence and confirmed dead code.
  8. Update docs/migrations.md alongside any implementation detail that changes during the work.

Verification

  • Use @effect/vitest Effect tests and temporary scoped database layers. Avoid shared mutable fixtures between persistence tests.
  • Verify migration 1 on an empty path, no-op restart on a current database, concurrent startup locking, transaction rollback, foreign-key enforcement, and future/unknown ledger rejection.
  • Verify every known prerelease JSON file, show document, chat database, chat envelope, and experimental database is rejected and never imported or modified.
  • Run repository contract suites against SQLite for profiles, settings, connections, shows, songs, microphones, mixes, and chats.
  • Stress rapid concurrent live mutations and streamed snapshots. Confirm committed order, no duplicate songs/messages, bounded latency, and recovery after interruption.
  • Package the desktop application and verify migration discovery, fresh startup, restart, backup, and startup-error presentation outside the source tree.
  • Run pnpm ready and repeat the dead-export/orphan-module scan.

Completion criteria

  • showtime.db is the only authoritative backend state store.
  • Migration 0001_initial represents the complete current schema.
  • No prerelease state is read, imported, rewritten, or silently ignored.
  • All repositories use Effect SQL and schema-validated query boundaries.
  • All multi-table domain changes are transactional and publish only after commit.
  • Repositories and network services cannot start before DatabaseReady.
  • Obsolete JSON/show/chat persistence and confirmed dead code are removed.
  • docs/migrations.md matches the implemented release policy.
