Sync engine

Replace point-in-time WebSocket reads with transactional, server-pushed full snapshots.

Outcome

A mounted client query receives an initial authoritative snapshot and remains subscribed over the existing Effect RPC WebSocket. After a successful mutation, the server invalidates the affected resource and sends every subscriber a newly read complete snapshot. This iteration deliberately sends whole arrays rather than deltas.

Correctness rule: a query snapshot and a mutation run inside the same transaction discipline. Subscribers can observe the state before a mutation or the durable state after it, but no partial intermediate state.

Effect v4 design

  1. Add a backend SyncEngine service as the single shared abstraction for synchronized queries and mutations. It owns Effect's transaction/serialization primitive and the Effect v4 Reactivity service.
  2. Implement query(key, effect) with Reactivity.stream. It runs immediately, reruns on matching invalidation, coalesces invalidations that arrive during a read, and unregisters when the RPC stream scope closes.
  3. Implement mutation(keys, effect) so the durable mutation completes successfully inside the transaction boundary before invalidation is published. Failed mutations publish nothing.
  4. Keep the Reactivity layer process-wide in the backend graph so all WebSocket connections share subscriptions and mutation notifications.

Shared keys move to the contracts package so backend and frontend cannot silently disagree about subscription identity.

Frontend changes

  • Use Atom RPC's native streaming-query path for all four list resources.
  • Remove client-only mutation invalidation as the source of synchronization; remote mutations must update every connected window, not only the initiating one.
  • Retain optimistic mutation reducers for immediate interaction feedback. The next server snapshot remains authoritative and reconciles temporary values.
  • Remove point-in-time SWR/focus refresh behavior where the persistent stream now owns freshness.

Transaction and failure behavior

  • File writes remain atomic through the existing temporary-file rename strategy.
  • The sync transaction prevents query/mutation interleaving around repository discovery, rename, delete, and show-file updates.
  • Invalidation occurs only after a successful durable operation and while ordering is still controlled by the transaction.
  • Effect reactivity queues at most one follow-up rerun while a query is already running, preventing unbounded snapshot work under mutation bursts.
  • WebSocket interruption closes the scoped stream registration; reconnect creates a new stream and immediately emits a fresh full snapshot.

Verification

  1. Unit-test the sync engine: initial snapshot, successful invalidation, no invalidation on failure, and serialized reads/writes.
  2. Expand the WebSocket integration test to keep a list stream open and prove a mutation pushes a second full snapshot without issuing another read RPC.
  3. Test isolation by show ID so a mutation in one show does not rerun another show's subscription.
  4. Run repository checks, all tests, and builds; fix contract/type fallout from changing list RPCs to streams.

Not in this iteration

  • Delta protocols, revision vectors, resumable offsets, or persisted event logs.
  • Cross-process synchronization or watching show files changed by an external program.
  • Changing the optimistic UI behavior beyond adapting it to authoritative streamed snapshots.
