Per-show chat and global notifications

Add reliable, profile-attributed, multi-channel show chat with persisted read state, reconnect catch-up, a normal show route, a live left drawer, and a reusable Effect-native toast bus.

Storage and domain model

  • Store all chat data in ~/.showtime/chats.db. No chat rows or chat metadata are written into <show-id>.showtime files.
  • Use SQLite foreign keys inside the chat domain, WAL mode, a busy timeout, explicit transactions, and monotonic integer message sequences for deterministic ordering and replay.
  • Model channels by show, messages by channel, and per-profile channel state with a last-read message sequence and a notifications-enabled flag.
  • Create a default General channel lazily for every show and allow users to add additional named channels. All profiles can read and write every channel.
  • Store the sender profile id on each message without a database foreign key to the profile file. Resolve the current profile name/color at render time; missing profiles render as Deleted profile.
  • Deleting a show removes its chat rows from chats.db in the same backend operation while keeping show files independent from chat storage.

Reliable synchronization and reconnect behavior

  1. Expose a profile-specific, per-show streaming snapshot RPC through the existing Effect reactivity layer. Every mutation invalidates the same show chat key, so active clients receive a new authoritative snapshot.
  2. Each snapshot carries channels, persisted unread counts/settings, the newest message sequence, and a bounded tail of messages per channel. A reconnect always receives current state even if transient live emissions were missed.
  3. Keep a versioned per-client notification cursor in local storage for each profile/show/channel. Compare that cursor with the authoritative snapshot rather than assuming uninterrupted delivery.
  4. If every missed message is present in the replay tail, publish one notification event for each eligible incoming message. If the cursor predates the replay tail, publish one summary event with the exact missed count for that channel.
  5. Advance notification cursors only after events have been handed to the global notification stream. Never notify for messages sent by the selected profile or for channels whose notifications are disabled.

Read state and notification eligibility

SituationBehavior
Selected channel is visible and scrolled to the latest messagePersist the newest message sequence as read and suppress chat toasts for those visible messages.
Selected channel is visible but the operator has scrolled upwardDo not advance read state; incoming messages remain unread and create notifications.
Another channel or another route is visibleIncoming eligible messages increment unread state and create notifications.
Channel notifications are disabled for the selected profileUnread tracking continues, but the global notification bus receives no toast event for that channel.
Connection resumes after a gapReplay individual missed notifications when bounded; otherwise show an exact per-channel summary.

Effect-native backend and frontend structure

  • Add Effect Schema contracts for channel ids, message ids, channel state, chat snapshots, and RPC payloads.
  • Use @effect/sql-sqlite-node and Effect SQL for database setup and queries. Put all SQL and transaction boundaries behind one ChatService.
  • Add reusable frontend chat atoms beside the existing show/song/profile atoms, including streaming state and mutations for channel creation, sending, reading, and notification preferences.
  • Create a global notification center backed by an Effect PubSub exposed as an Effect Stream. Producers publish typed notification events; one React bridge consumes the stream and renders Base UI Toast components.
  • Keep chat eligibility/catch-up policy separate from toast rendering so future system-wide notification producers can reuse the same bus without depending on chat components.

UI composition

  • Add /shows/$showId/chat as the full chat route and add Chat to the desktop show sidebar.
  • Add a Chat icon beside Songs in the mobile show bottom navigation while retaining the centered Live action.
  • In Live, open the same chat workspace from a left-side shadcn Base UI Drawer. Keep song navigation usable when the drawer is closed and make channel selection available inside the drawer.
  • Build the conversation with the shadcn Base UI Message, Bubble, and Message Scroller components. Use their default visual language and only add layout classes and existing Showtime CSS variables.
  • Show channels with unread badges, a small add-channel flow, and a per-channel notification switch. Keep profile switching reachable wherever messages can be sent.
  • Use an accessible multiline composer with explicit send status, stable optimistic behavior, and retryable errors. Empty or oversized messages are rejected consistently in schema and UI.

  • Unit-test notification cursor catch-up, own-message exclusion, visible-at-bottom suppression, muted channels, replay-tail overflow summaries, and duplicate snapshot suppression.
  • Run formatting, type checks, package tests, and production builds.

This prerelease change intentionally initializes the current chat schema directly and includes no migration framework. Database failures remain explicit, while live delivery always recovers from the authoritative SQLite state.
