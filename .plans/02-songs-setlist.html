Plan 02

Songs and Setlist

Add persistent songs to a show, let engineers arrange the setlist by dragging, and provide a focused song page for notes and per-mix microphone assignments. The design stays minimal, predictable, and usable during soundcheck and a live show.

Scope

Contracts, persistence, RPC, reactive state, sidebar, all-songs view, and song detail view.

Primary workflow

Create a song, reorder it, open it, add notes, and choose microphones for every mix.

Reliability rule

Optimistic interactions must visibly roll back and report an error when persistence fails.

Product decisions

DecisionPlan
Song notesOne optional song-level notes field, shown before all mix cards.
Mix assignmentsEach song stores zero or more microphone IDs for each mix. An empty selection is valid.
OrderThe active array order is canonical. The displayed song number is its one-based position, not a persistent identity.
DeletionSoft-delete with deletedAt. Deleted songs disappear from the active setlist; surviving songs close the numbering gap.
Missing referencesDeleted mixes or microphones are excluded from the UI. Their stale IDs are tolerated on read and pruned on the next song edit.

Data model

Add a dedicated song.ts contract. Keep persistence normalized by referencing existing mix and microphone IDs instead of copying their names, numbers, or colors. 

Song {
  id: SongId                         // branded "song_" + standard suffix
  name: SongName                     // trimmed, non-blank
  artist: SongArtist                 // trimmed, non-blank
  notes?: string                     // absent when blank
  mixAssignments: Array<{
    mixId: MixId                     // at most one entry per mix
    microphoneIds: Array<MicrophoneId> // unique IDs, stable mic-list order
  }>
  createdAt: DateTimeUtc
  updatedAt: DateTimeUtc
  deletedAt?: DateTimeUtc
}
  • Add songs: Schema.Array(Song) to ShowFileDocument and initialize it to [] for newly created shows.
  • Use the order of non-deleted entries in songs as the setlist order. Reordering changes array order and refreshes the show file timestamp.
  • Validate assignment uniqueness and reject duplicate microphone IDs within one mix assignment.
  • Do not store a mutable song number. This prevents number/order drift after deletion or drag operations.

  • The header shows the computed song number in the same visual language as the sidebar, then editable name and artist. The ellipsis menu is on the far right and initially contains only Delete song.
  • Deleting requires the standard confirmation dialog. After success, navigate to All songs; on failure, keep the page and show the error.
  • The Notes card comes first and uses a plain multiline textarea. Save on blur with a small saving/error state; remove the property when the trimmed value is empty.
  • Render one mix card for every active mix, ordered like the Mixes screen. Each card displays its label/name and a clean list of active microphones with checkboxes or toggle rows.
  • Use existing @/components/ui defaults. Only apply layout classes; preserve the repository rule against restyling shared primitives.
  • Loading, empty, disconnected, and save-failure states must remain readable without shifting the page structure.

All songs and sidebar

All songs view

  • Show an ordered, full-width list rather than cards so sequence is immediately scannable.
  • Each row has a drag handle, computed number, song name, artist, and a link/open affordance.
  • The whole row may be a drag preview, but only the handle initiates dragging to avoid accidental moves while navigating.
  • Provide keyboard reordering from the handle and announce movement through an ARIA live region.
  • Disable additional reorder commits while one is in flight. Keep an optimistic local order, then rollback on failure.

Setlist sidebar

  • Replace placeholderSongs with the live songs atom.
  • Show the current one-based number, truncated song name, and artist badge.
  • Make the Setlist plus action create a song through a small dialog asking for name and artist, then navigate to the new song.
  • Reflect optimistic create, delete, and reorder results immediately and consistently in both sidebar and main content.
  • When no songs exist, keep All songs visible and show a friendly empty state with an Add song action.

RPC surface and service behavior

RPCBehavior
ListSongs(showId)Return active songs in canonical setlist order.
CreateSong(showId, name, artist)Trim and validate values, append to the active setlist, and return the song.
EditSong(showId, id, name, artist, notes, mixAssignments)Validate referenced active mixes/microphones, normalize assignments, update atomically, and return the song.
ReorderSongs(showId, orderedSongIds)Require every active song ID exactly once; preserve deleted records; persist one atomic order change.
DeleteSong(showId, id)Set updatedAt and deletedAt together.

Add songsRpcReactivityKey(showId). All successful mutations invalidate that key so the sidebar, list, and detail page converge after reconnects or partial optimistic updates. Route handlers should delegate to SongService; file update locking and atomic writes remain owned by ShowFile.

Implementation sequence

  1. 1. Contracts and persistence

    Define Effect schemas and branded IDs, export them, add songs to the show document, initialize new files, and extend ID generation. Update fixtures immediately so schema tests continue to represent valid files.

  2. 2. Effect-native song service

    Implement all operations through ShowRepository and ShowFile.update. Reuse existing error translation patterns. Centralize normalization and reference validation in shared helpers rather than duplicating it across operations.

  3. 3. RPC and reactive atoms

    Expose typed RPCs and handlers, wire the service layer, then create a song atom family with SWR behavior and optimistic create/delete/reorder/edit reducers. Keep server results authoritative.

  4. 4. Sidebar and creation flow

    Remove placeholders, render live songs, enable the plus button, and share one creation dialog between the sidebar and the empty all-songs state.

  5. 5. All-songs drag ordering

    Build the accessible sortable list. Prefer the drag-and-drop package already present in the workspace; if none is installed, add a maintained keyboard-capable library rather than implementing pointer geometry locally.

  6. 6. Song detail page

    Build the header, notes card, mix cards, microphone selection controls, and delete workflow. Derive displayed labels from current mix/microphone queries so edits elsewhere appear without rewriting songs.

  7. 7. Failure and load testing

    Exercise rapid reorders, reconnects, deleted references, concurrent edits, and write failures. Confirm that atomic persistence, rollback behavior, and final ordering remain predictable.

Testing plan

Contract and backend

  • Accept valid songs and reject blank names/artists, malformed IDs, duplicate assignments, and duplicate microphone IDs.
  • Create appends; edit preserves identity/creation time; delete soft-deletes; list filters deleted songs.
  • Reorder rejects missing, duplicate, foreign, or deleted IDs without modifying the file.
  • Deleted mix/microphone references do not crash list/read behavior.
  • Parallel updates serialize through the show-file semaphore and always leave valid JSON.

Renderer and workflow

  • Sidebar and all-songs list display identical order and numbering.
  • Pointer and keyboard reorder produce the same ordered ID payload.
  • Failed reorder rolls back and announces the failure.
  • Notes and microphone selections survive navigation and refresh.
  • Deleting the open song routes safely to All songs.
  • Empty, loading, stale-with-refresh, and hard-failure states are covered.

Acceptance criteria

  • A user can create a song with a required name and artist and see it immediately in both setlist views.
  • Every active song has a stable ID and timestamps, supports optional notes, and may be soft-deleted.
  • The song number always matches its current position in the active ordered setlist.
  • The all-songs list can be reordered with pointer and keyboard input, and the order survives restart.
  • The detail header contains number, name, artist, and an ellipsis menu whose sole option is Delete.
  • Notes appear first; one minimal card follows for every active mix, with assignable active microphones.
  • Failures never silently discard edits or leave sidebar and page ordering permanently inconsistent.
  • All new contracts, services, and critical interaction reducers have automated tests.
