Connection scopes

Add least-privilege, extensible connection-management scopes while keeping every persisted and exchanged payload at version: 1. This is intentionally a breaking shape change because Showtime is prerelease and migrations are not required.

Scope model

The user-facing “Allow this client to manage connections” switch maps to three small permissions. It is off by default. Keeping the individual values in a shared, typed list lets later UI expose more granular choices without changing the authorization model.

ScopeAllowsDoes not allow
connections:read List paired/pending clients and load pairing information/QR links. Create or revoke anything.
connections:create Create a new single-use invitation with an explicit scope set. Read the list or revoke access by itself.
connections:delete Delete pending invitations and revoke paired clients. Create invitations or read state by itself.

The management switch grants all three scopes. A delegated manager may only grant scopes it already holds, preventing privilege escalation if more scopes or granular UI are added later.

Data and transport changes

  1. Define the scope literals, scope schema, management bundle, validation helpers, and scope-bearing shared connection types in @showtime/shared.
  2. Store scopes on both pending invitations and paired clients. Copy the exact invitation scopes into the client record when the invitation is consumed, and include them in the version-1 pairing response/browser credential record.
  3. Extend the connection store with an atomic authorization check for a client capability plus required scope, and retain the existing session admission/revocation locking.
  4. Add authenticated HTTP management functions for state, invitation creation, pairing info, and deletion. Each function checks its own narrow scope on the authoritative server-side client record. Invalid credentials return 401; valid credentials lacking a scope return 403. Request validation rejects unknown scopes and delegated scope escalation.
  5. Keep the native desktop bridge as the trusted owner path. Adapt its invitation call to accept scopes and reuse the same manager functions.

Interface and responsive behavior

  1. Add the off-by-default management switch immediately below the client-name input. Its copy explains that it permits viewing, adding, connecting, and removing clients.
  2. Introduce one browser/desktop connection-management client so the dialog does not duplicate host bridge and authenticated HTTP behavior.
  3. Show the Connections trigger to scoped browser clients on desktop widths in the normal header. Keep it off the live route, matching the existing host behavior.
  4. On mobile widths, show the trigger only in the show route’s mobile header, where there is room for an action. Do not put it in the compact app title bar or live UI.
  5. Make the management, creation, and QR dialogs fit small viewports, respect safe areas, scroll internally, use compact/icon triggers where necessary, and keep tap targets and labels accessible.
  6. Hide the host-only “Allow connections” setting from delegated clients. Delegated managers can perform only the read/create/delete operations represented by their scopes.

Verification

  • Store tests cover default-empty scopes, propagation on pairing, and scope checks.
  • Backend integration tests prove each endpoint rejects missing permissions, accepts the required scope, prevents delegated privilege escalation, and preserves version 1.
  • Browser tests cover scope validation/persistence and management request behavior.
  • Run repository type checks, unit/integration tests, and production builds.
  • Inspect desktop and mobile layouts in the collaborative browser when available.
