Plan 03

Live route

Replace the Live placeholder with a large, read-only song view optimized for quick scanning during a show. Keep the current position and elapsed live time visible in the title bar, and make previous/next navigation available at the screen edges.

Primary workflow

Open Live, read the current song, and move backward or forward without editing anything.

Performance rule

Derive the view from the existing reactive song, mix, and microphone atoms; add no polling except the local elapsed-time display.

Safety rule

The route is strictly read-only. No live-screen control may mutate songs, notes, assignments, mixes, or microphones.

Target layout

This mockup communicates hierarchy and placement. The implementation must use the default project Button, Badge, and Card styles rather than restyling shared UI primitives.

Live session and timer

  • Entering /live/$showId starts a live session if that show has no active local session; reopening or refreshing the same live route resumes its existing start time.
  • Persist startedAt per show in a small renderer-owned live-session module. The timer is UI state, not show configuration, and must not trigger RPC writes.
  • Compute elapsed time from Date.now() - startedAt on each tick instead of incrementing a counter. This prevents drift when rendering stalls or the machine is under load.
  • Update at most once per second, pause the interval while the document is hidden, and immediately recompute on visibility return.
  • The Back action explicitly ends and clears the local live session before returning to the show. Normal rerenders, reconnects, and route remounts must not reset it.
  • Format elapsed time as HH:MM:SS, allowing hours above 23. The badge always includes the word LIVE so color is not the only signal.

Navigation and route state

Store the selected song in the URL as a search parameter, for example /live/show_123?song=song_456. This makes refresh and renderer remount behavior deterministic without introducing mutable global selection state.

  • If the URL references an active song, display its current position in canonical setlist order.
  • If the parameter is absent or invalid, select the first active song and replace the URL. If the current song is deleted during Live, select the song now occupying the same index, falling back to the new final song.
  • Previous and Next replace only the search parameter, preserving the live session. Support ArrowLeft and ArrowRight when focus is not inside an interactive control.
  • Buttons use explicit labels such as Previous song: Yellow and Next song: Clocks. Disabled edge buttons remain visible so layout never shifts.
  • Keep the side controls outside the scrolling content column and large enough for quick pointer use. At narrow widths, anchor them near the bottom corners so they do not cover song content.

Read-only projection

LiveSongView = {
  position: currentSongIndex + 1
  total: activeSongs.length
  name: currentSong.name
  artist?: trim(currentSong.artist) || undefined
  mixes: orderedActiveMixes.flatMap(mix => {
    assignment = currentSong.mixAssignments.find(item => item.mixId === mix.id)
    microphones = activeMicrophones
      .filter(mic => assignment?.microphoneIds.includes(mic.id))
      .map(mic => ({
        number: mic.number,
        color: mic.color,
        name: songOverride(mic.id) ?? mic.name ?? `Microphone ${mic.number}`
      }))
    return microphones.length ? [{ mix, microphones }] : []
  })
  notes?: trim(currentSong.notes) || undefined
}

Put this pure projection in a shared module and unit-test it independently. It centralizes filtering, ordering, fallback labels, and stale-reference handling instead of spreading those rules through JSX.

Loading and failure behavior

Predictable display

  • Show the standard loading empty state only when no cached songs exist.
  • When stale data exists during refresh or reconnect, keep the current song visible and do not move focus.
  • Ignore deleted or unknown mix and microphone IDs instead of failing the entire view.
  • Use stable IDs as React keys so a data refresh does not recreate every card.

Empty and hard failure

  • An empty setlist shows No songs in this setlist with only a Back action.
  • A hard load failure with no cached data shows a concise connection error and a retry action.
  • Missing assignments show no mix section; missing notes show no Notes card.
  • Navigation remains disabled until a valid current song is available.

Implementation sequence

  1. 1. Pure live projection

    Build and test the function that joins songs, mixes, microphones, assignments, and song-level microphone-name overrides. Reuse the existing color-class mapping.

  2. 2. Session timer

    Create the per-show start/resume/end abstraction and drift-free elapsed hook. Keep storage and interval cleanup out of route components.

  3. 3. Title bar API

    Extend TitleBar with composable Live content slots so the current song, position, and timer fit without embedding atom reads in the shared title bar.

  4. 4. Read-only song content

    Render the large centered identity, responsive non-empty mix cards, active microphone rows, and optional notes card using shared UI defaults.

  5. 5. Navigation

    Add URL-based selection, edge buttons, keyboard shortcuts, disabled boundaries, and deterministic recovery when the selected song disappears.

  6. 6. Reliability pass

    Exercise cached refresh, reconnect, renderer remount, rapid navigation, setlist changes during Live, and long-running timer behavior before replacing the placeholder route.

Testing plan

Projection and timing

  • Projects only active, assigned microphones and non-empty mixes.
  • Resolves song override, global name, and fallback label in that order.
  • Ignores stale IDs while preserving source order.
  • Formats zero, one hour, and more than 24 hours correctly.
  • Resuming uses the stored start time; ending clears only that show.

Route and interaction

  • Missing song parameter selects the first song.
  • Buttons and arrow keys navigate one song without wrapping.
  • First/last disabled states and accessible names are correct.
  • Deleting/reordering the current song selects a deterministic neighbor.
  • The Live screen exposes no inputs or mutation calls.
  • Cached content stays visible through a failed refresh.

Acceptance criteria

  • The title bar shows the current song prominently, x of y songs, and a destructive badge with elapsed live time.
  • The content centers a large song number and name, with a smaller muted artist only when present.
  • Previous and Next controls sit at the left and right edges, move exactly one song, and disable at setlist boundaries.
  • Mix cards lay out next to one another and contain only active assigned microphones.
  • Each microphone row contains only its colored number and resolved name; song-specific names win.
  • A read-only Notes card appears below the mix grid only when notes exist.
  • The timer survives rerenders, reconnects, and route remounts without drift and stops when Back ends Live.
  • Loading, empty, stale, missing-reference, and hard-failure states never expose editing controls or crash the route.
