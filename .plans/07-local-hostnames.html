Predictable .local addresses and port 8585

Give each Showtime desktop server an easy local-network address while preserving the existing authenticated pairing, WebSocket RPC, reconnect, and IP-address fallback paths.

Review summary

Canonical addresses

  • The first successful claimant uses http://showtime.local:8585.
  • Conflicting servers use http://showtime-1.local:8585, then showtime-2.local:8585, and so on.
  • The production/LAN HTTP and WebSocket server moves from 34987 to 8585. Vite's development-only renderer remains separate because it cannot share the backend's listening port.

The port must remain visible in a typed or copied browser URL. A .local A/AAAA record resolves a host, not an HTTP port. DNS-SD can advertise port 8585 to service browsers, but entering bare showtime.local still makes an ordinary browser try port 80. This plan intentionally does not open port 80 or add a second redirect server.

Port 8585 is currently unassigned in IANA's service-name and port-number registry. It is in the user-port range, so binding does not require administrator privileges. “Unassigned” is not a permanent reservation for Showtime; a bind conflict must still fail clearly rather than silently selecting another port.

Current architecture to preserve

  • packages/backend/src/index.ts already owns one Effect-managed Node HTTP server for the static web build, pairing endpoints, connection-status endpoint, and authenticated Effect RPC WebSocket upgrades.
  • ConnectionStore persists per-client capabilities, tracks live sessions, interrupts revoked clients, and survives backend restarts.
  • NetworkAddresses already creates private-IPv4 pairing candidates used by the Electron connection dialog.
  • The browser consumes the single-use #pair=… fragment, stores credentials under that origin, removes the fragment, and reconnects the RPC client through the current page origin.
  • The “Allow connections” switch gates static hosting and RPC admission and disconnects active remote clients when disabled.
  • The desktop runtime is scoped through ManagedRuntime and is disposed during Electron shutdown.

The implementation must extend this graph. It must not create a second HTTP server, a second RPC transport, or an unauthenticated path around the existing connection capability.

Resulting flow

Effect runtime starts
  → TCP 8585 successfully binds on 0.0.0.0
  → local-discovery scoped fiber probes its preferred .local name over mDNS
  → winner announces A record + _http._tcp DNS-SD service for port 8585
  → Connection dialog prefers http://showtime[-N].local:8585/#pair=…
  → browser pairs through the existing POST /pair/:token endpoint
  → browser reconnects through ws://showtime[-N].local:8585/rpc/:clientId/:capability

If mDNS is blocked or unsupported
  → TCP server and desktop remain healthy
  → dialog clearly falls back to the existing private-IP pairing URLs

Naming rules

SituationRequired behavior
No existing Showtime responder Probe and announce showtime.local.
One or more names already claimed Probe candidates in order and claim the first available exact label: showtime-1, showtime-2, and so on. Never expose library-default forms such as showtime-(2).local.
Simultaneous startup Use RFC 6762 probing and record-data tie-breaking. “First” means the server that wins the uniqueness probe; wall-clock launch order cannot be guaranteed when probes are simultaneous.
Normal restart Try the last successfully announced label first. This keeps the browser origin stable, so a server previously known as showtime-1.local does not unexpectedly become showtime.local and strand saved browser credentials.
Saved label is now owned elsewhere Run conflict resolution again, select the next exact suffix, atomically persist it, and show the new URL in the connection dialog.
A lower suffix later becomes free Do not promote a running server. Stable origins and reconnect reliability take priority over closing cosmetic gaps in the numbering.
Graceful shutdown or connections disabled Send mDNS goodbye records before releasing the responder so clients do not retain avoidable stale cache entries.
Crash or power loss On restart, probe rather than trusting cached state. Stale cache entries are not treated as ownership; an active responder must defend a name.

Persistence means a lone server may continue to use a previously assigned suffix after moving to a different network. That is deliberate: existing bookmarks and saved credentials are more important than always reclaiming the shortest label.

mDNS implementation decision

Use @homebridge/ciao behind a repository-owned adapter. It is a pure TypeScript/JavaScript RFC 6762/6763 responder, performs uniqueness probing, publishes host and DNS-SD records, tracks interface changes, and supports goodbye packets without adding fragile native build dependencies on Windows.

The dependency cannot be used unmodified. Its current conflict policy emits hostnames like showtime-(2).local, and its interface-republish failure path contains a process-level exit. Both conflict with Showtime's explicit naming requirement and live-show reliability policy.

  1. Pin the reviewed @homebridge/ciao version and use pnpm's checked-in patched-dependency mechanism.
  2. Patch only the hostname suffix formatter/parser so the first conflict maps to -1, the next to -2, and already-suffixed persisted names resume at the correct internal sequence.
  3. Patch the republish failure path to notify the adapter instead of calling process.exit. The adapter moves to a degraded state, disposes the failed responder, and retries in a scoped background fiber.
  4. Add regression tests that fail if a dependency upgrade restores parenthesized names, exits the process, leaks a responder, or omits goodbye cleanup.
  5. Keep every third-party type and callback inside MdnsAdvertiserLive; the rest of Showtime depends only on its own Effect service contract. Any later replacement of the library is then local.

Do not hand-build an mDNS responder from raw UDP packets. Correct simultaneous probing, cache-flush semantics, ongoing conflict detection, interface churn, IPv4/IPv6 behavior, and packet sizing are too failure-prone to recreate for this feature.

Effect-native backend design

1. Central endpoint configuration

  • Create one shared local-endpoint module with production port 8585, base label showtime, label schema, suffix formatting/parsing, and URL constructors. Remove production/test copies of 34987.
  • Keep a test-layer override for ephemeral ports. Production must never auto-fall back from 8585, because a different runtime port would make the advertised and remembered address unpredictable.
  • Continue binding the HTTP server to 0.0.0.0 and the Electron RPC client to loopback. Advertise only address families actually served; with the current IPv4 bind, disable AAAA publication to prevent clients preferring an unreachable IPv6 record.

2. LocalDiscovery service

Introduce a backend service with a narrow contract:

  • Current state: disabled, probing, announced with hostname, or degraded with a typed/redacted reason.
  • An idempotent setEnabled(boolean) operation serialized inside the service.
  • An Effect that returns the current hostname pairing candidate only after announcement succeeds.

Build the live layer with Layer.scoped and Effect.acquireRelease. Acquisition owns the responder, service, event listeners, retry fiber, and state reference; release interrupts retries, sends bounded goodbye packets, removes listeners, and shuts the responder down exactly once. Use Effect Schema for persisted labels, Ref/SubscriptionRef for observable state, Semaphore for transitions, Deferred or Queue to bridge library events, and typed Effect.tryPromise boundaries for every promise callback.

3. Dependency ordering and failure containment

  • Make discovery depend on the acquired HttpServer service so port 8585 is listening before any DNS-SD announcement becomes visible.
  • Because of that layer dependency, discovery finalizers run before the HTTP server finalizer and can withdraw the address cleanly.
  • Run advertising under a scoped supervisor with capped exponential backoff and jitter. Retry UDP/socket, temporary no-network, and interface-republish failures without producing an unhandled rejection or terminating Showtime.
  • Deduplicate repeated logs. Record state transitions and selected non-secret hostname, but never invitation tokens, client capabilities, or full pairing URLs.
  • mDNS failure is degraded, not fatal: the show database, desktop renderer, HTTP server, RPC loopback client, and IP pairing candidates continue to work. A TCP 8585 bind failure remains fatal and produces the existing actionable startup dialog.

4. Persistent hostname preference

  • Store a small schema-versioned discovery file under the existing .showtime data directory using the shared atomic JSON helper.
  • Persist only the successfully announced label, never a candidate still being probed.
  • There is no migration: a missing file means first-run probing from showtime. A malformed non-security-critical discovery file is quarantined/ignored with a warning and regenerated after successful announcement rather than crashing the backend.

5. Connection enable/disable integration

  • Initial advertisement follows persisted connectionsEnabled. Disabled remote hosting must not advertise a usable Showtime service.
  • Disabling connections first closes admission through settings, interrupts active remote sessions, then withdraws mDNS records. Repeated disable calls are no-ops.
  • Enabling connections opens the existing HTTP/RPC gate and starts announcement. If announcement is degraded, private-IP pairing remains available and the UI explains the fallback.
  • Serialize this lifecycle with the existing connection-management transition so UI state is reported only after the requested local state is settled.

Connection and UI integration

  1. Replace the IP-specific candidate DTO with a schema-derived union for hostname and ip-address candidates. Include a human label, host, complete pairing URL, and optional interface name. Validate DTOs at the Electron IPC boundary.
  2. ConnectionManager.pairingInfo asks LocalDiscovery and NetworkAddresses concurrently, puts the announced .local URL first, and retains all valid private-IP candidates as fallbacks.
  3. The connection dialog defaults the QR code and copy action to http://showtime[-N].local:8585/#pair=…. Its selector labels that option “Showtime local address” and keeps adapter-specific IP choices underneath. Use existing UI component defaults; only layout changes are needed.
  4. While probing, show a short non-technical “Finding an easy local address…” state. On degradation, select the best IP automatically and say that the easy name is unavailable on this network; do not block pairing or expose raw socket errors.
  5. No browser credential or reconnect algorithm changes are needed. Pairing and RPC URLs remain same-origin, so the current stored-connection resolver automatically uses the hostname and port from window.location.

Moving from port 34987 to 8585 changes the browser origin. Previously paired browsers cannot read credentials stored under the old origin and must scan a new invitation once. The prerelease/no-migration permission makes this an accepted breaking change. Do not keep an old-port redirect or compatibility listener.

Security and network boundaries

  • mDNS publishes only the hostname, minimal _http._tcp service metadata, and port 8585. It must never publish show names, device names, invitation tokens, client IDs, capabilities, or pairing URLs in TXT records.
  • The hostname is discovery, not authorization. Existing single-use invitation tokens and per-client RPC capabilities remain mandatory.
  • .local is link-local. It is not promised across routed VLANs, guest-network isolation, enterprise multicast filtering, VPN boundaries, or access points that suppress multicast.
  • Keep IP URLs because some venue networks and client operating systems disable or filter mDNS. The UI should never imply that a missing .local name means the server itself is down.
  • Verify packaged-app firewall behavior for TCP 8585 and mDNS UDP 5353. Do not request broad firewall exceptions beyond the executable and required protocols.
  • Plain HTTP retains the trusted-LAN confidentiality limitation documented by the existing connection design; this change does not weaken or claim to solve it.

Verification plan

  1. Unit-test label parsing/formatting, DNS-label length limits, exact suffix sequence, persisted preference, corrupt-state recovery, URL encoding, and port 8585.
  2. Use a fake MdnsAdvertiser layer to deterministically test disabled, probing, announced, conflicted, degraded, retried, and disposed state transitions with Effect's test clock where timing is involved.
  3. Run isolated responder integration tests proving one process gets showtime.local, the next gets showtime-1.local, a third gets showtime-2.local, and simultaneous starts never share a unique hostname.
  4. Test restart continuity: a suffixed server reclaims its persisted label when free, advances when occupied, and never promotes itself while running.
  5. Assert the patched dependency never invokes process.exit on an injected republish failure and that the adapter retries without an unhandled rejection.
  6. Capture mDNS packets in integration tests or a test decoder to verify A, PTR, SRV, TXT, cache-flush, and goodbye records; assert SRV port 8585 and absence of secrets.
  7. Prove announcement begins only after TCP is listening and shutdown withdraws discovery before the HTTP layer is released.
  8. Extend backend HTTP/WebSocket tests for showtime.local:8585-style Host headers while preserving unauthenticated 404s, one-time pairing, RPC authorization, presence, revocation, disable, and restart reconnect.
  9. Extend UI/platform tests so the hostname candidate is preferred, IP fallback remains selectable, and a hostname page constructs its WebSocket URL from the same origin.
  10. Perform packaged Windows, macOS, and Linux smoke tests with two machines on one LAN, two Showtime servers, restart/crash recovery, Wi-Fi reconnect, firewall prompt/rules, Android/iOS browsers, and a multicast-blocking guest network.
  11. Run pnpm ready and a source search confirming active production/test code no longer contains port 34987.

Acceptance criteria

  • A single enabled Showtime server is reachable at http://showtime.local:8585 on an mDNS-capable local network.
  • Additional concurrent servers receive exact, unique showtime-1.local, showtime-2.local, … addresses without manual configuration.
  • The advertised DNS-SD service and every production pairing/RPC URL use port 8585; the backend never silently changes ports.
  • Existing invitation consumption, credential storage, WebSocket authorization, reconnection, disable, and revocation semantics remain intact.
  • No mDNS failure, interface churn, rejected promise, or dependency callback can terminate the Showtime process.
  • Disabling connections withdraws the advertisement and blocks remote hosting; re-enabling restores it.
  • When .local is unavailable, users can still connect through an automatically offered IP URL.
  • Graceful runtime disposal sends goodbye records and closes all responder resources without delaying app exit indefinitely.

Explicitly out of scope

  • Making bare http://showtime.local work without :8585 by also binding privileged/default port 80.
  • Routing .local across VLANs, the public internet, guest isolation, or networks that suppress multicast.
  • Replacing trusted-LAN HTTP with automatic TLS certificates.
  • Maintaining a compatibility listener or browser-storage migration from port 34987.
  • Using DNS-SD browsing to build a list of all Showtime servers in the web UI; this change only publishes stable addresses.
