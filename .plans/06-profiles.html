Profiles

Add show-independent engineer profiles with shared management and a local selection on every client.

Outcome and behavior

  • Persist profiles centrally in ~/.showtime/profiles.json. Each profile has an id, name, color, created timestamp, and updated timestamp.
  • Create one profile named “Default” with sky color and a normal generated profile id when no profile file exists.
  • Persist the centrally configured default profile id with the profiles. Setting a different default updates only that shared fallback.
  • Store each browser/client’s selected profile id in versioned local storage. If it is missing, malformed, or points to a deleted profile, resolve to the shared default and repair local storage.
  • Profiles are visual only in this iteration; no show, connection, permissions, or data mutation is attributed to them.

UI composition

LocationPresentation
Desktop show layoutA profile select directly below the Live button in the sidebar footer, grouped with an adjacent edit button.
Mobile show layoutThe same compact selector/edit button appears in the show overview/settings route so management remains reachable without crowding live controls.
Index routeA fixed bottom-right selector/edit group, clear of the show list and mutation status.

The select renders the profile color as a round dot and the name as text. The adjacent settings icon opens one management dialog built from default shared UI components.

Management dialog

  1. List profiles as compact item rows with a color-dot popover and name in one input group, followed by default and delete actions.
  2. Auto-save a changed name on blur and save color choices immediately, serializing overlapping edits per row.
  3. Prevent only the current shared default from being deleted. Once another profile is made default, the original “Default” profile can be deleted like any other.
  4. Add profiles with a sensible generated name and sky color, then allow immediate editing.
  5. Keep error and pending states visible and predictable; refresh authoritative profile state after every mutation.

Effect-native implementation

  • Add contract schemas and RPCs for list, create, edit, delete, and set-default operations.
  • Add a ProfileService using Effect FileSystem, Path, Clock, Ref, Schema, Semaphore, and atomic JSON persistence. Expose updates through the existing SyncEngine snapshot model.
  • Add frontend profile atoms beside shows/mixes/microphones/songs so reconnects and mutations share existing retry and invalidation behavior.
  • Put selection parsing and local-storage synchronization in one profile module and expose it through a small React hook/provider.
  • Add the shadcn/base button-group component once and reuse one ProfileSwitcher across every responsive placement.

Correctness and verification

  • Unit-test first-run default creation with a normal id, timestamp updates, validation, current-default deletion protection, default switching, deletion fallback, and persistence reload.
  • Test local selection decode, repair, cross-tab storage updates, and deleted-profile fallback.
  • Run repository checks, tests, and builds.
  • Launch the app and use Windows computer control to validate index placement, desktop sidebar placement, mobile show access, selection persistence after reload, auto-saving edits, adding, setting default, and current-default deletion protection.

Breaking schema changes require no migration for this prerelease implementation; corrupt or structurally invalid profile files should fail loudly rather than silently discard operator data.
