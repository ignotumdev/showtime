Trusted local-network connections

Let a phone, tablet, or laptop scan Showtime once, load the bundled web app directly from the desktop instance, and reconnect to its Effect RPC WebSocket without internet access.

Outcome

The desktop backend runs one HTTP server on the LAN. That server serves the production web build and upgrades authenticated requests to the existing Effect RPC WebSocket. A “Connect device” dialog in the Electron renderer presents a QR code containing the current LAN address and a high-entropy pairing capability. The browser consumes the capability once, stores it in local storage, removes it from the address bar/history, and uses it on every later WebSocket connection.

This is capability-based access for a trusted local network, not public-internet authentication. Merely discovering Showtime's IP or loading its JavaScript must not grant access to show data.

User flow

Desktop toolbar → Connect device → choose a reachable network if needed → scan QR
Phone browser → HTTP app loads locally → pairing fragment is saved and erased → WebSocket connects
Later visit to the same address → saved capability is reused automatically
  1. Add a desktop-only connection button to the existing title bar. It opens a normal shared UI dialog using the defaults from @/components/ui.
  2. The dialog shows a large QR code, the equivalent short copyable URL, the selected interface name, and plain-language guidance that both devices must be on the same trusted Wi-Fi or wired network.
  3. When several useful adapters exist, rank private IPv4 addresses ahead of other LAN addresses and let the user switch candidates. Exclude loopback, link-local, internal, and obvious virtual/tunnel adapters by default, with a secondary “Other networks” list so unusual show networks still work.
  4. The QR URL is http://<lan-ip>:34987/#connect=<capability>. The fragment is never sent in the HTTP request. A synchronous bootstrap step validates and saves it before React, the router, or the RPC client starts, then calls history.replaceState to leave a clean #/ URL.
  5. Subsequent visits to that same origin read the saved, versioned connection record. Invalid or revoked credentials show a dedicated reconnect screen instead of an endless loading state.

Security and lifecycle decisions

ConcernDecision
RPC authorization Use a cryptographically random 256-bit capability in an unguessable WebSocket path, /rpc/<capability>. Unknown paths receive a generic 404 and never reach RPC handlers.
HTTP disclosure The static app is readable by the LAN, but APIs and show data are not. Keep the secret in the URL fragment during pairing so request lines, access logs, proxies, and referrers do not receive it.
Restarts Persist the capability in a small backend connection-settings file with restrictive file permissions and atomic replacement. Do not regenerate it at every launch; otherwise “scan once” cannot work.
Revocation Add “Reset connected devices” to the dialog. Rotation immediately changes the accepted RPC path and QR code; existing sockets are interrupted and saved browser records cease to authenticate.
Browser storage Store a schema-validated, versioned record in local storage. Never put the capability in application logs, error messages, analytics, DOM text beyond the QR/copy action, or query parameters.
Network trust Show a concise warning not to enable sharing on guest/public Wi-Fi. Plain HTTP is acceptable only for the explicitly scoped trusted-LAN design; the capability protects authorization but HTTP does not prevent an on-path observer from seeing later WebSocket traffic.
Address changes Saved pairing survives app restarts while the origin remains reachable. A DHCP address change changes browser origin and requires rescanning; state this honestly. Avoid mDNS in this iteration because support and name conflicts are less predictable on venue networks.

Effect-native backend design

  1. Introduce a ConnectionSettings Effect service responsible for loading, validating, creating, persisting, and rotating the capability. Its live layer uses Effect FileSystem, Path, scoped resources, typed errors, and a small Node cryptographic-random adapter. Tests receive deterministic in-memory/test layers.
  2. Introduce a NetworkAddresses Effect service that snapshots usable interface addresses and returns ranked, labeled connection candidates. Isolate Node's networkInterfaces() behind the service rather than calling it from Electron or React.
  3. Refactor makeBackendLayer so a single HttpRouter, NodeHttpServer, and scope own both static files and WebSocket RPC. Use Effect v4's HttpStaticServer/HttpServerResponse.file support, including content types, conditional requests, and cache headers. Do not build a parallel Node request handler.
  4. Serve exact assets when present and fall back to index.html only for safe GET/HEAD app routes. Reject traversal and encoded traversal, return real 404s for missing asset-like paths, and set index.html to no-cache while fingerprinted assets may be cached immutably.
  5. Replace the caller-supplied rpcPath with the settings service's capability path. Backend options become the stable bind host/port, web-root path, and optional test overrides. Bind to 0.0.0.0:34987; Electron still connects through 127.0.0.1 to avoid adapter dependence.
  6. Expose a narrow backend ConnectionManager service to Electron for the current local RPC URL, LAN pairing candidates, and rotation. Electron IPC returns structured, schema-validated data and runs service effects through the already scoped ManagedRuntime.

Frontend and Electron changes

  • Extend the preload bridge with typed connectionInfo and resetConnections operations while retaining contextIsolation; no Node primitives enter the renderer.
  • Put connection-record parsing, fragment capture, URL construction, and storage behind one shared browser module. Model decoding and failures with Effect Schema, Option, and typed errors; use Effect's browser key-value-store layer if its v4 API fits the bootstrap boundary.
  • Change resolveRpcWebSocketUrl precedence to: Electron bridge, valid saved browser connection, explicit development override. Remove unauthenticated /rpc same-origin fallback.
  • Add a connection state around the frontend runtime so missing credentials, authentication failure, server unavailable, reconnecting, and connected are distinguishable. The remote web UI gets a simple “Scan the QR code shown in Showtime” page when no saved connection exists.
  • Generate QR SVG locally from a bundled npm library—no remote image endpoint, fonts, script, DNS, or CDN. Keep QR generation in a shared module and render it only in the Electron connection dialog.
  • Keep the existing web build as the single renderer artifact. Desktop packaging already copies apps/web/dist; pass that resolved directory to the backend in production. In development, keep Electron on Vite for hot reload and serve the latest built web artifact on the LAN, with a clear startup error if it is absent rather than silently serving a broken page.

Failure behavior

  • A port bind failure prevents desktop startup and reports the actionable port conflict, preserving today's fail-fast behavior.
  • A settings read/write failure is typed and fatal at startup; Showtime never falls back to an ephemeral secret that would break saved devices.
  • No usable LAN address disables the QR with “No local network found”; the local Electron client continues working through loopback.
  • A stale address produces an ordinary unreachable page and is fixed by rescanning after the desktop shows its new address.
  • An invalid/stale capability loads the shell but the WebSocket is rejected; the UI clears no data automatically and asks for a new scan.
  • Transient disconnects continue using Effect Socket retry behavior and the streaming RPCs republish authoritative snapshots after reconnect.
  • Rotation is serialized, atomically persisted, and only reported successful after the server has switched credentials and interrupted old sessions.

Verification

  1. Unit-test settings creation, stable reload, atomic rotation, corrupt-file failure, redaction, and deterministic test layers.
  2. Unit-test interface filtering/ranking with loopback, Wi-Fi, Ethernet, VPN, IPv4, IPv6, and no-network fixtures.
  3. Integration-test static index/assets, MIME and cache headers, SPA fallback, HEAD, 404 behavior, and traversal rejection.
  4. Prove an unauthenticated or wrong-path WebSocket cannot call RPC while the persisted capability can.
  5. Prove two LAN-style clients receive streamed updates, reconnect after interruption, and lose access immediately after rotation.
  6. Test fragment capture: saved before client creation, removed from history, malformed values rejected, and saved values restored after a simulated restart.
  7. Test Electron bridge precedence and ensure capability-bearing values are not included in snapshots/log assertions.
  8. Build the web and packaged desktop artifacts, inspect that all assets are bundled, and perform a real-device airplane-mode test on a local access point.
  9. Run pnpm ready and fix all type, test, and build fallout.

Explicitly out of scope

  • Internet relay, cloud accounts, remote access, telemetry, or any dependency on outside connectivity.
  • Per-user identity/permissions or independent device revocation; rotation revokes all paired browsers together.
  • Automatic TLS certificates. Trusted-LAN HTTP is an intentional first iteration, with its on-path confidentiality limitation disclosed above.
  • mDNS/service discovery, native mobile apps, push notifications, and background browser operation.
  • Persisting offline edits in the browser; the backend remains authoritative.
